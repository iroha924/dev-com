# grill

推奨の設定: gpt-6.1-sol・medium（議題がデータの形・権限・セキュリティ・本番の手順・リリースに触れるなら gpt-6.1-sol・high）。比べ方は AGENTS.md の「モデルと effort の案内」

親（この skill を読んでいる Codex）が叩き台を作り、`design-challenger` に反論させ、合意するまで議論する。
**持ち主に返すのは合意した後。**途中の往復は報告しない。実装は、報告の後に持ち主が頼んだときだけ。

**事実は調べて決め、持ち主には決定だけを聞く。**コード・設定・資料を読めば分かることを持ち主に聞かない。

## 議論が崩れる形（先に読む）

同じモデルどうしの議論は、正しかった側が相手の理由づけに流されて誤った側へ寄りやすく、早く合意しすぎる（複数の研究での実測。[判断の根拠](#判断の根拠)）。次の 3 つで防ぐ。

- **譲るには新しい根拠が要る。**ファイルと行、コマンドの出力、URL と引用のどれかが新しく出たときだけ立場を変える。もっともらしい説明だけでは譲らない。親も子も同じ。
- **叩き台は「ある案」として渡す。**親が書いた・持ち主が考えた、とは書かない。誰の案かが分かると、その側に寄る。
- **往復は 4 回まで。**長く続けるほど流されやすい。上限で合意を作らない。

## 1. 材料を集める

- 議題と、持ち主がすでに決めていること（議論の対象にしない）を書き出す。持ち主の言葉に近い形で。
- 関係するコード・設定・資料を読み、参照したファイルと URL を控える。Work Item の番号があれば `ado` skill の手順で読む。
- 決まらないと叩き台がまったく書けない点だけを、推奨案を付けて先に持ち主に聞く。それ以外は仮定を置いて進み、仮定は「前提」に書く。

## 2. 叩き台を作る

次の節で書く。壁打ちで書けない節は「未定」と書いてよい。叩き台には番号（r1、r2…）を付け、直すたびに上げる。

| 節 | 中身 |
|---|---|
| 議題 | 何を決めるかを 1 文で |
| 持ち主の決定 | 1 で書き出したもの |
| 目的 | 何ができるようになるか。終わった状態を観測できる言葉で |
| 範囲と対象外 | やること、やらないこと |
| 前提 | 確かめた事実と出典（file:line、URL と確認日）。置いた仮定は「仮定」と書く |
| 方針（要件定義なら要件） | どう作るか、何を満たすか。要件は下の型で書く |
| 比べた案 | 採る案と棄却する案を 1 行ずつ、理由付きで |
| リスクと戻し方 | 起きうることと、起きたらどう戻すか |
| 完了条件 | 何を流す・見れば終わったと言えるか |
| 決まっていないこと | **3 個まで。**影響の大きい順（範囲 > セキュリティ・データ > 使い勝手 > 技術の細部）に残し、残りは仮定にして「前提」へ |

要件は、条件と振る舞いが分かれる型（EARS）で書く。**異常系を抜かさない。**CI やパイプラインの要件では、失敗・タイムアウト・再実行のときの振る舞いが漏れやすい。

| 型 | 書き方 |
|---|---|
| 常に | 〈対象〉は〜する |
| きっかけ | 〜したとき、〈対象〉は〜する |
| 状態 | 〜の間、〈対象〉は〜する |
| 機能があるとき | 〜が有効な場合、〈対象〉は〜する |
| 異常系 | もし〜なら、〈対象〉は〜する |

## 3. design-challenger を起動する

`spawn_agent` を次の引数で呼ぶ。`agent_type: "design-challenger"` と `fork_turns: "none"` は必ず付ける。

| 引数 | 値 | 理由 |
|---|---|---|
| `agent_type` | `"design-challenger"` | 省くと既定の役になり、反論の指示が載らない |
| `fork_turns` | `"none"` | **省くと既定の `"all"` になり、親の会話を全部引き継ぐ。**それでは独立した判断にならない |
| `task_name` | `grill_` と議題を表す英小文字・数字・`_`（例 `grill_retry_policy`）。起動し直すときや議題を変えたときは末尾を変える（`grill_retry_policy_r2`） | 2 往復目以降の宛先になる。同じ名前の子が残っていると起動に失敗する |
| `reasoning_effort` | 既定は渡さない（親の effort を継ぐ）。親が medium 以下で動いていて、議題がデータの形・権限・セキュリティ・本番の手順・リリースに触れるときだけ `"high"` | 直すのが難しい失敗に関わる判断にだけ時間をかける。親が high より上で動いているときに渡すと、かえって下がる |
| `message` | 下の「1 往復目に渡すもの」 | |

**1 往復目に渡すもの**: 議題、持ち主の決定（議論の対象にしないと書く）、叩き台（「ある案」として）、参照先。
**自分の結論や、予想される反論は渡さない。**渡すと、子はそれを確かめるだけになる。

起動したら、`wait_agent` に `timeout_ms: 600000`（10 分）を渡して待つ。子の返答は親に届く。`wait_agent` 自体は中身を返さず、時間切れは子が止まったことを意味しない。子は自分でコードや資料を確かめるので、1 往復に数分かかるのはふつう。

## 4. 議論する

返ってきた指摘を 1 件ずつ確かめる。指摘は主張として扱い、コードか一次情報で裏を取ってから受け入れる。再現できないことを理由に受け入れを止めない（コードを読めば確定するものは、読めば足りる）。「好み」「将来の拡張性」のような分類の名前だけで退けない。退けるなら根拠を付ける。

2 往復目以降は、同じ子へ `followup_task` で次を送り、また `wait_agent` で待つ。`target` は、`spawn_agent` の結果か `list_agents` に出た子のパス（root から起動したなら `/root/<task_name>`）。前回の要点は書き直さない。

- 指摘 ID ごとに「受け入れ / 根拠付きの反論 / 保留」。反論には新しい根拠を付ける
- 叩き台の新しい番号と、直した箇所だけ
- 新しく分かった事実

事実で決まる点（API がそのバージョンにあるか、設定が効くか）は、議論で決めずに、どちらかが確かめて決める。

**終わる条件**: 子が、最新の叩き台について `no_major_open: true` を返した。争点が無ければ 1 往復で終えてよい。

- 往復は 4 回まで。残った点は報告の「持ち主に決めてほしいこと」へ回す。**上限に達したことを合意と書かない。**
- 3 回続けて時間切れになった（合計 30 分）ら、`list_agents` で子の状態を見る。`running` のままなら `interrupt_agent` で止める。`errored` のときと、返答が決まった形になっていないときも含め、名前の末尾を変えて新しい子を 1 度だけ起動し直す。それでも返らなければ議論を止めて、そう報告する。**子が黙ったことを合意と数えない。**
- 議題が途中で変わったら、新しい子を起動する。前の議題の前提を引きずらないため。

## 5. 報告する

| 節 | 中身 |
|---|---|
| 結論 | 合意した案を 3〜7 行で。何が決まり、何をしないか。合意した叩き台の番号。合意していなければ、合意していないことと、残った点の数を先に書く |
| 合意した案 | 2 の節で、議論を反映した最後の叩き台 |
| 持ち主に決めてほしいこと | 双方に根拠があって決着しなかった点と、持ち主にしか決められない点（優先度、担当、予算、社内の決まり）。1 点ずつ番号を振り、**推奨案を先に書いて「はい」で推奨案を採れる問いにする**。選択肢ごとに、こちらの根拠・相手の根拠・不利を添える |
| 確かめられなかったこと | 未確認の前提と、それが外れたときに変わる箇所 |
| 議論の記録 | 往復の回数、受け入れた指摘と取り下げた指摘を ID ごとに 1 行。返らなかった往復があればそれも |

- 既定ではチャットに出すだけ。持ち主が保存先を言ったときだけ、その場所に md で保存する（UTF-8、BOM なし）。
- 持ち主が「持ち主に決めてほしいこと」に答えたら、それを合意した案に反映して見せる。答えが案の前提を崩すなら、同じ子へ 1 往復だけ送って確かめる。これは 4 往復の上限の外とする。子がもう使えなければ、名前を変えて新しい子を起動し、答えを反映した案を渡す。
- 合意した内容を Work Item に書くのは、持ち主が頼んだときだけで、`work-item-ready` の手順で行う。
- それ以外で、議論を終えた子へ追加で送らない。

## 判断の根拠

- 同じモデルどうしの議論で、正しかった答えが相手の理由づけで誤りへ変わる: Wynn ほか「Talk Isn't Always Cheap」（arXiv 2509.05396、2025）、Bertalanič・Fortuna「The Cost of Consensus」（arXiv 2605.00914、2026）
- 迎合で早く合意しすぎる: Yao ほか「Peacemaker or Troublemaker」（arXiv 2509.23055、2025）
- 誰の発言かを伏せると偏りが減る: Choi ほか「When Identity Skews Debate」（arXiv 2510.07517、2026）
- 事実は調べて決定だけを聞く、推奨案付きで聞く: Matt Pocock の grill-me / grilling（https://github.com/mattpocock/skills）
- 決まっていない点を 3 個までに絞り、残りは仮定にする: GitHub Spec Kit（https://github.com/github/spec-kit）
