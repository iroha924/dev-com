# work-item-ready

ADO の読み書きは `ado` skill の手順に従う。

## 1. 読む

- 対象の Work Item: タイトル・説明・受け入れ条件・状態・Iteration・親・子・関連リンク・コメント。
- 関係するコード: 説明に出てくる名前（モジュール、設定キー、パイプライン名、プロンプトのファイル名）で、今いるリポジトリを検索する。リポジトリの外のことは推測しない。

## 2. 出す

| 節 | 中身 |
|---|---|
| 着手を妨げる不足 | 決まっていないと実装の向きが変わるものだけを **3 個まで**、影響の大きい順（範囲 > セキュリティ・データ > 使い勝手 > 技術の細部）に。それぞれに推奨案と、誰に聞けば決まるかを添える。それ以外は仮定を置き、「前提と推測」に書く。コードや資料を読めば分かることは聞かずに調べる |
| 受け入れ条件の案 | 検査か確認の手順で合否が決まる文にする。「適切に」「十分に」を使わない。条件と振る舞いを分けて書き（「〜したとき、〜する」「もし〜なら、〜する」）、**失敗・タイムアウト・再実行のときの振る舞いを抜かさない** |
| 検証方法 | 条件ごとに、何を流す・見れば満たしたと言えるか |
| 分割案 | 1 つが 1 日程度で終わり、それぞれ単独でレビューできる単位。依存の順を付ける |
| 前提と推測 | Work Item に書かれた事実と、こちらの推測を分けて並べる |

担当者・優先度・見積もり（ストーリーポイント、残作業時間）は決めない。案を求められたら、根拠を添えて「案」として出す。

## 3. 書く（ユーザーが頼んだときだけ）

- 受け入れ条件の更新: `Microsoft.VSTS.Common.AcceptanceCriteria` を HTML で書く（`<ul><li>...</li></ul>`。本文中の `<` `>` `&` はエスケープする）。既存の値を消すことになるなら、消える内容を見せる。
- 子タスクの作成: 作る件数と、各タスクのタイトル・説明・親を一覧で見せて承認を取る。親へのリンクは `System.LinkTypes.Hierarchy-Reverse`。Iteration と Area は親と同じにする。
- 送り方は `ado` skill の「書く」。作った Work Item の番号を一覧で返す。
