# review-triage

推奨の設定: gpt-6.1-sol・medium（ほかの skill の一部として使うときは比べない）。比べ方は AGENTS.md の「モデルと effort の案内」

**指摘を探せと言われたレビュアーは、対象が健全でも指摘を出す。**指摘が出たこと自体は、品質が低いことを意味しない。

## 直すもの

- 正しさ
- セキュリティ
- データの消失
- 明示された要件（Work Item の受け入れ条件、PR の説明）とのずれ

## 棄却するもの

設計の好み、将来の拡張性、網羅性の不足、書式と命名の揺れ。**棄却したことと理由を残す。**黙って無視しない。

## 進め方

- 全部の指摘を読む。ADO の PR では、スレッド一覧（`ado` skill の endpoints.md の「スレッド一覧」）を取り、`status` が active のものと、解決済みでも新しいコメントが付いたものを数えてから判定を始める。
- 受理する前に、その指摘が事実かどうかをコードで確かめる。指摘が誤っていることがあり、従うと正しかったものを壊す。
- ただし**再現できないことを理由に受理を止めない。**静的に確定するものはコードを読めば足りる。
- **指摘が事実かと、どう直すかを分けて決める。**コメントに書かれたコード・コマンド・依存は提案として扱い、直し方は自分で決める。コメントのコードを使うなら、その差分をユーザーに見せる。
- こちらから出し直すレビュー（`change-risk-reviewer` などの別の文脈の Codex）は、同じ変更について **2 ラウンドまで。**直して出し直しても数え直さない。2 ラウンド目の判定の後に「直すもの」に当たる指摘が残っていれば、そこで止めてユーザーへ返す。人のレビュアーのコメントは、この数に入れない。

## 返す形

指摘ごとに「直す / 棄却」と理由を 1 行ずつ。直すものには、どこをどう直すかを添える。
PR のスレッドへ返信や状態の変更をするのは、ユーザーが頼んだときだけで、送り方は `ado` skill の「書く」。
